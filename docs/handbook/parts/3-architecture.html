2 · System designArchitecture: one program, one database

One program, with the boundaries of the services it may later become. One database that understands geography. One phone app for three kinds of user.

Decisions that shape the code

  • A modular monolith. The design names separate services; the code keeps their boundaries as modules in one process. A module can be split out later without a redesign, and until then there is one thing to deploy.
  • Checks live in the UPDATE. Stock holds, a picker's claim on an order, an agent's claim on a trip, an order's change of state, one-time codes and "a lot is taken in once" all use an update that carries its own condition. Nothing reads a value, checks it in Python and writes it back.
  • Events cannot be lost or invented. An event row is written in the transaction that made the change. If the change rolls back, so does the event. Modules that listen run inside that transaction too, and where the order of two listeners matters a test holds it in place.
  • Retries are safe. Writes at the dock take an idempotency key: the same request sent twice is done once and answered the same.
  • PostgreSQL only. The prototype also ran on SQLite. Removing it allowed real geography queries, through the PostGIS extension, and one database behaviour to test against.

Accounts

  • No passwords: a six-digit code by email, valid 10 minutes, 5 wrong tries, single use, stored only as a keyed hash.
  • One request a minute and five an hour per address (fifteen on staging). The answer is the same whether or not the address has an account.
  • A customer's token opens no staff endpoint, and a staff token no customer endpoint.
  • An agent sees customers' addresses, so the platform team makes an agent's account. On staging a setting lets anyone sign up as one.

The phone app

  • One app, three roles. The account's role decides the home screen.
  • One interface, two back ends. Every screen talks to one typed client. Given a server's address it is the real API; without one it is demo data built into the app.
  • It installs from a file: an Android build made on the development server, with staging's address built in. Until 24 November the app ran only inside Expo Go, a host app, loaded from a laptop.

2 · System designWhat runs on AWS

One environment, staging, in Mumbai. Nobody can deploy to it by pushing code.

From a commit to running

  1. A person signed in to AWS chooses a commit. The repository is public; a push can start tests and nothing else.
  2. Tests on CodeBuild: a fresh PostGIS database, the migrations checked against the models, the whole suite, the phone app type-checked. The result shows on the commit in GitHub.
  3. Build: an image tagged with the commit id, which cannot be overwritten.
  4. Roll out: the new version must be healthy before the old one stops. One that never gets healthy is rolled back.
  5. Smoke test from outside the network.

A commit whose tests have not passed is not deployed.

Decisions on AWS, and why

  • Nothing in GitHub can build or deploy. With a public repository, "a push deploys" would let anyone who can push deploy. A signed-in person chooses the commit.
  • The database login is read when a connection opens. AWS changes the master password every seven days. A container handed it once at start would have failed before the demo.
  • The caller's address is believed only from inside the network. The rate limit is per address, and the header carrying it can be forged from outside.
  • One copy of the app, and no second environment. The timed jobs run inside the app, so two copies would run them twice. A second environment would double the daily cost.
