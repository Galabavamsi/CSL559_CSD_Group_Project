Three things a viewer should be told

  • The phone app has run on one phone, on demo data only. On a Galaxy M34 (Android 16) in Expo Go: sign-in, the shop, cart, hold, checkout, payment, the order, and the farmer's home (section 5). It has not run there against the real backend, and registering a farm, which needs the location prompt, was not walked through. The other screenshots are the same app's web build at phone size.
  • The recording ran on the project's development server, with the real backend code and a real PostgreSQL, not on staging. Sign-in codes were read from that server's log, where the development email backend writes them. On AWS the code goes by email and the log never holds it.
  • Bangalore's two hubs still carry the dark store's groceries (milk, bread, rice). They are demo data from the prototype. Bhilai's hubs start empty and hold only what farms bring, which is why the recording is set there.

Known limits of what is built

  • The bill follows the pack, not the actual weight. A pack promises its weight; tolerance is not modelled.
  • Every lot gets the next morning window; the number of lots a hub can check in one window is not limited.
  • The hub's bins know ambient, chilled and frozen; the design's "cool" and "cold" share chilled.
  • One copy of the app runs. The timed jobs and the live feed live inside it, so a second copy needs those moved out first.
  • Email is a weaker second channel than a phone number: whoever reads the inbox can sign in.
  • On the web build the session is kept in the browser's local storage; on a phone it is in the secure store.
  • The staff logins are shared demo accounts behind one generated password per environment.
  • Push-triggered test runs wait for the GitHub connection to be authorised in the AWS console.
