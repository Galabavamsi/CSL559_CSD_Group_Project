6 · System designHow it is built

One program, with the boundaries of the services it may later become. One database that understands geography. A production-style home on AWS that nobody can deploy to by pushing code.

Decisions that shape the code

  • A modular monolith. The design names separate services; the code keeps their boundaries as modules in one process. A module can be split out later without a redesign, and until then there is one thing to deploy.
  • Checks live in the UPDATE. Stock holds, job claims, one-time codes and "a lot is taken in once" all use an update that carries its own condition. Nothing reads a value, checks it in Python and writes it back.
  • Events cannot be lost or invented. An event row is written in the transaction that made the change. If the change rolls back, so does the event.
  • Retries are safe. Writes at the dock take an idempotency key: the same request sent twice is done once and answered the same.
  • PostgreSQL only. The prototype also ran on SQLite. Removing it allowed real geography queries and one database behaviour to test against.

Geography

  • Which hub serves an address: delivery zones are sets of H3 hexagons (resolution 9, about a tenth of a square kilometre each) mapped to hubs. A lookup is one indexed read.
  • Which hub takes a farm's lot: a nearest-neighbour query on a GiST index over the hubs' points, then the capacity checks of section 4.
  • A farm's own location is kept only if the phone's fix is within 50 m.
  • Opening a hub creates the hub, its 18 bins and its logins and recalculates every zone in one transaction: the new hub takes over the cells it is nearest to.

Accounts

  • Six-digit code by email, valid 10 minutes, 5 wrong tries, single use, stored only as a keyed hash.
  • One request a minute and five an hour per address. The answer is the same whether or not the address has an account.
  • Access token 60 minutes, refresh token 30 days and single use. A refresh token seen twice ends every session of that user.
  • A customer's token opens no staff endpoint, and a staff token no customer endpoint.

On AWS

From a commit to running

  1. A person signed in to AWS chooses a commit. The repository is public; a push can start tests and nothing else.
  2. Tests (CodeBuild): a fresh PostGIS, the migrations checked against the models, the hub pages' scripts syntax-checked, the whole suite, the phone app type-checked.
  3. A status on the commit in GitHub: passed or failed.
  4. Build: an image tagged with the commit id, which cannot be overwritten.
  5. Roll out: ECS starts the new version, waits until it is healthy, then stops the old one. A version that never gets healthy is rolled back.
  6. Smoke test from outside the network.

A commit whose tests have not passed is not deployed. Going back is deploying an older commit.

Decisions on AWS, and why

  • Nothing in GitHub can build or deploy. With a public repository, "a push deploys" would let anyone who can push deploy. A signed-in person chooses the commit.
  • The database login is read when a connection opens. AWS changes the master password every seven days, next on 30 November. A container handed the password once at start would have failed days before the demo.
  • The caller's address is believed only from inside the network. The rate limit is per address, and the header carrying it can be forged from outside.
  • One copy of the app, for now. The timed jobs and the live feed run inside it. The load balancer, the standby database and the rollback are ready for more.
